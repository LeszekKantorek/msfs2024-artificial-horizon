## Why these details matter

The [work organization model](../docs/work-organization.md) defines the hierarchy.
The planning skill owns Task preparation, while [Task execution](iterative-development.md#accepted-plans-and-handoffs) owns context checks, consultation, and reporting.

| Planning property | Reason |
| --- | --- |
| Self-contained Task | Terra can execute in another session without reconstructing intent from temporary files or a previous conversation |
| Decisions before dependent execution | Consequential choices are resolved once, while routine implementation remains with Terra |
| Iterative planning | Investigation results justify the next Tasks without turning an unconfirmed cause into a correction plan |
| Main-conversation feedback | Resolved gaps, consultation reasons, and decision results remain available for later JSON session review |
| Result-based parent completion | Finishing the current Tasks does not hide an unmet Work Item or Initiative criterion |

| Planning detail | Reason | Current altitude-trend example |
| --- | --- | --- |
| Current code and source authority | Prevent stale knowledge from overriding a newer requirement | The trend overlays the left-side ticks and retains six-second prediction |
| Decisions before decomposition | Prevent a layout preference from becoming an undocumented assumption | Keep the four-pixel trend clip inside the altitude allocation |
| Explicit invariants | Keep a visual change from changing unrelated behavior | Preserve freshness, alarm history, prediction, and SVG node identity |
| Actual module boundaries | Make the steps executable without speculative refactoring | Change allocation in layout and SVG creation order in altitude composition |
| Completion conditions | Define when a step produces its required result | The tape ends at the panel edge and has no external trend region |
| Scenario inputs and expected results | Turn requirements into reproducible checks | +1500 ft/min predicts +150 ft and draws 60 px upward |
| Evidence selected by failure risk | Prevent a passing test from answering the wrong question | Inspect painted overlap because bounding boxes cannot prove layer order |
| Baseline and matched captures | Make before/after comparisons attributable to the change | Repeat the same values, viewports, routes, and browser |
| Review and acceptance limits | Expose work that test results alone cannot establish | Separate independent review and actual phone checks from desktop validation |

## Sources and limits

Interpret planning evidence under these limits:

* Select evidence that addresses the changed behavior and its failure risks.
* Report independent review separately from validation.
* Treat instruction reviews and scenario walkthroughs as evidence of document coverage.
  Claims about agent behavior, model selection, or GitHub publication require observed results of those operations.
