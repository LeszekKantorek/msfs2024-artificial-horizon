## Accepted decisions and evidence limits

* Capture the current application's native log in active flight before changing application code. Compare available application fields after grouping. Straight autopilot flight with the same aircraft is sufficient; identical values and timestamps are unnecessary.
* Use one definition containing pitch, roll, and the 17 optional inputs, followed by one persistent request. Definition registration requires one `AddToDataDefinition` call per variable with the same definition ID.
* Define field mappings in JSON using exact SimConnect SDK 2024 SimVar names, unit names, and datatype identifiers, without aliases. Build both the native definition and packet decoder from this configuration; only the target `field` identifier belongs to the application.
* Remove the four redundant diagnostic inputs: degree readings and repeated radian readings of pitch and roll. Convert radians locally. Their removal requires no cost measurement or benchmark.
* Use two independent parameters: raw `SIM_FRAME interval` in simulation-frame events and an ordinary SSE snapshot period in milliseconds. Do not reopen alternatives such as repeated `ONCE`, `SECOND`, separate field rates, or a single combined parameter.
* Send full snapshots containing the latest available values, including unchanged values. Use one receipt timestamp for the complete accepted grouped sample. Remove per-field receipt timestamps and independent field expiry: freshness expires the whole sample together, all or nothing. Per-field value validation remains separate from freshness; IAS history retains the timing needed for trend calculations.
* The server expires the complete sample after `1.5 * sse_interval_ms` without a new accepted SimConnect packet, measured from its common native receipt timestamp. SSE publication never refreshes that timestamp. Preserve the existing IAS history limit and algorithm, including its 500 ms gap boundary; slow acquisition can leave IAS available without a trend.
* The browser delivery deadline is 1.5 times the effective SSE period after receipt of the last accepted live snapshot. For 2000 ms, it is 3000 ms. This accepted requirement replaces the fixed one-second browser silence deadline.
* Keep immediate initial delivery and prompt detected state and availability transitions. Maintain shared acquisition and bounded latest-state storage for slow clients.
* Official SimConnect and SDK behavior govern the implementation. Demo is an implementation to adapt and test, not evidence of official behavior.
* There is no separate baseline-measurement Subtask, performance campaign, or requirement to justify removal of redundant inputs. The before/after logs in Subtask 1 establish field availability only. Original issue criteria concerning performance or device evidence remain unconfirmed unless supported by applicable evidence; this plan does not silently satisfy or rewrite them.

## Current implementation and accepted changes

| Boundary | Current behavior | Consequence |
| --- | --- | --- |

The source deadline is settled: use 1.5 times the SSE period, independently of the raw frame interval. The server measures from native packet receipt; the browser measures from SSE snapshot receipt. A native gap reaching this deadline expires the whole sample, even if the gap results from the configured SimConnect interval. Neither unchanged-value SSE publication nor connectivity messages renew native freshness. Preserve the IAS history algorithm. Subtasks 1 and 2 retain the transitional 1000 ms whole-sample threshold. Subtask 3 introduces the SSE configuration and replaces that threshold with the accepted final formula. This delivery sequence does not change the final behavior.

Apply these ownership and cleanup rules:

* Validate the mandatory mapping before starting source acquisition. Carry failure classification explicitly through runtime results so a terminal error cannot fall into the reconnect branch.
* On terminal native/session failure, perform these actions in order:

  1. Stop accepting packets from the failed connection generation.
  2. Clear the current sample and pending live updates.
  3. Immediately publish `disconnected`, bypassing any ordinary SSE schedule. Make this state available to current and new subscribers before invoking native close.
  4. Attempt native close and resource cleanup once. If close fails, preserve the existing resource-retention behavior and do not start a new session.

* Keep `disconnected` throughout delayed or failed cleanup. Preserve both the primary failure and any cleanup failure in diagnostics. Do not depend on the current supervisor's post-acquisition publication to invalidate the sample: update the terminal path so publication precedes cleanup. The supervisor must preserve this terminal state.
* Keep HTTP available after a runtime acquisition failure. Browser transport can remain connected while source state is disconnected; this publication rule does not guarantee delivery over a stalled network. A late subscriber sees the terminal state, never the previous live sample. Reserve `invalid` for semantic attitude invalidity.
* Give a concise actionable error on stderr even with `--log` disabled. **Implementation guidance.**

* Final CLI contract: `--simconnect-interval`, decimal integer from 0 through 4294967295 inclusive, default 0. Pass it unchanged to the SDK `interval` argument for `SIM_FRAME`; do not convert it to milliseconds. Reject negative, fractional, and overflowing inputs before opening the source. The SDK declares `interval` as `DWORD`; zero requests every period. It explicitly mentions a very large interval such as `DWORD_MAX` to effectively suspend transmissions, so do not reject the maximum as reserved or reinterpret it as an application sentinel. This is the API input range, not a guarantee of useful live cadence at every value. See the [SDK request contract](https://docs.flightsimulator.com/msfs2024/flighting/programming-apis/simconnect/api-reference/events-and-data/simconnect_requestdataonsimobject/) and [Microsoft DWORD definition](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/262627d8-3418-4627-9218-4ffe110850b2).
* Test CLI acceptance and unchanged native argument wiring for 0, 1, 4294967294, and 4294967295; reject 4294967296, negatives, and fractions. Use widened arithmetic for Demo frame scheduling so calculations at the maximum cannot wrap to zero. Test those boundaries with controlled frame counters rather than waiting for real frame events.
* Preserve all-or-nothing sample freshness and the existing IAS history algorithm. Keep the transitional source timeout at 1000 ms in this Subtask; do not derive a different threshold from native frame cadence. Test native gaps just below, at, and above 1000 ms with zero and nonzero interval settings. The final `1.5 * sse_interval_ms` timeout and its combined configuration checks belong to Subtask 3.
* Preserve the existing IAS history reset at a gap of at least 500 ms. A fresh speed value does not guarantee an available trend; do not extend the history window or change the trend algorithm to compensate for slow acquisition.
* Wire the parameter through the existing source configuration and preserve it across source reconnects. Keep a single definition/request and current shutdown ownership.
* Building on the configured-type and grouped-response support delivered in Subtask 1, schedule Demo requests on due scenario frames according to verified SDK interval semantics. Advance scenario time independently of delivery; preserve pause, gaps, equal-value holds, and skipped-frame behavior. Preserve the grouped-response behavior and evidence limits established in Subtask 1.

## Subtask 3 — Schedule SSE snapshots and update browser freshness

**Parent and prerequisites.** Task #102; depends on the grouped provider and native interval support from Subtasks 1 and 2. The two-parameter contract is specified: `--simconnect-interval` defaults to 0 and `--sse-interval-ms` defaults to the accepted 500 ms. Names and numeric ranges are resolved in this draft; implementation and publication remain separately authorized.

**Outcome.** An independent ordinary SSE period with full latest-state snapshots, prompt transitions, and a matching browser delivery watchdog.

**Scope.** CLI/application configuration, shared publication scheduling, SSE serialization, browser client and frame scheduler, integrated tests, and owning user/contract documentation. No per-client history, separate acquisition per subscriber, or new per-field timestamp contract.

**Context.** [Application](../../src/application.rs), [provider publication](../../src/providers/simconnect/runtime.rs), [telemetry channel](../../src/telemetry.rs), [SSE handler](../../src/http/sse.rs), [browser client](../../web/telemetry/client.js), [frame scheduler](../../web/frame-scheduler.js), [telemetry contract](../../docs/telemetry-contract.md), and [SSE tests](../../tests/http_sse.rs).

**Implementation guidance.**

* Final CLI contract: `--sse-interval-ms`, decimal integer from 1 through 1431655764 inclusive, default 500 ms. Omission selects the default; zero, negative, fractional, and out-of-range inputs fail at startup. The default is user-selected, not a measured optimum. Zero cannot represent a periodic schedule or a positive freshness deadline.
* Replace the arbitrary 60000 ms cap with the technical single-timer bound `floor((2^31 - 1) * 2 / 3) = 1431655764 ms` (about 16.57 days). The browser schedules a freshness deadline of 1.5 times this period using `setTimeout`, whose signed 32-bit timeout argument must remain representable. This is a limit of the selected scheduling approach, not an SSE protocol limit; supporting longer periods would require scheduling long waits in chunks, which is outside this Task. See the [HTML timer interface](https://html.spec.whatwg.org/multipage/webappapis.html#windoworworkerglobalscope-mixin) and [timer algorithm](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers). Use checked/widened server arithmetic and validate the same range in browser metadata.
* Preserve half-millisecond deadlines for odd periods. When calling the browser timer, round the positive remaining delay upward to an integer millisecond, then recheck the monotonic deadline on callback. At the maximum supported period, the deadline delay is 2147483646 ms; the next period would require a rounded delay of 2147483648 ms and is rejected. Timer scheduling and network delivery are not real-time guarantees: acceptance of 1 ms does not promise 1 ms delivery or rendering. Do not silently clamp or rewrite the user's interval.
* Test 1, 500, 2000, 60001, and 1431655764 as accepted SSE periods; reject 0, negatives, fractions, and 1431655765. Use controlled clocks to verify odd-period rounding, maximum deadline arithmetic, matching metadata validation, and absence of timer overflow without real long waits.
* Pass the effective SSE period to the provider freshness logic as well as delivery configuration. Replace the transitional 1000 ms source threshold with `1.5 * sse_interval_ms` everywhere whole-sample freshness is evaluated, including lifecycle and snapshot construction. Expire at or beyond the threshold from the last accepted native packet; use duration arithmetic that preserves half milliseconds for odd periods. At 2000 ms SSE, native silence expires the whole sample at 3000 ms; the accepted 500 ms default gives a 750 ms source deadline. Preserve the separate 500 ms IAS history boundary.
* Carry required `sse_interval_ms` in every telemetry snapshot, including the initial snapshot and explicit non-live states. The browser receives effective configuration again on reconnect. Update producer, consumer, and fixtures together; missing or invalid metadata is a protocol error handled through the existing client failure path, without a legacy fallback.
* Keep shared current source state updated on every native receipt independently of ordinary SSE notifications. Initial connections and reconnects must read that current state and its actual receipt age, even between ordinary ticks. Do not use an old published snapshot as the current source cache: its age can falsely become stale while native input is healthy. Preserve globally monotonic sequence ordering; each emitted regular live snapshot must be newer than the preceding emission even when values are unchanged. An initial snapshot acknowledges the current channel version so subscription catch-up cannot immediately replay an older snapshot.
* Use one shared monotonic ordinary-publication schedule. At each due tick, publish the latest valid live state even when values are unchanged, with age calculated from actual source receipt. Skip missed ticks rather than queueing catch-up events. A sample arriving inside a period waits at most until the next tick, subject to source validity; do not add another periodic gate in each SSE handler.
* Keep the initial current snapshot immediate. Publish detected pause, disconnect, invalidity, source-stale, recovery, and optional availability changes immediately. Distinguish availability transitions from ordinary value changes. Urgent publications do not postpone the next ordinary tick. Cancel pending live output when the source becomes non-live; never release an obsolete live snapshot after a transition.
* Keep bounded latest-state semantics. Slow clients can skip intermediate states; prompt publication does not guarantee delivery of every transient state over a stalled connection. Reconnect reads current state, not queued history.
* For each accepted live sequence, set browser expiry to local receipt time plus `1.5 * sse_interval_ms`. Use that deadline in both client and frame scheduler. Duplicate or rejected sequences and comment heartbeats do not extend it. Apply explicit server state and availability immediately; preserve EventSource error/reconnect behavior. `sample_age_ms` remains source-age information and does not reintroduce the old fixed browser timer.

**Acceptance criteria.**

* With fast native acquisition and SSE at 2000 ms, unchanged healthy live snapshots continue every period and the browser remains live between them. Silent stream loss expires the display at 3000 ms after the last accepted live snapshot in controlled-clock tests.
* A source that becomes stale, paused, disconnected, or invalid just after an ordinary tick publishes the detected transition promptly. Recovery and optional removal/restoration caused by newly received values also bypass the ordinary period. Source expiry removes all sample indications together; it cannot produce staggered per-field expiry. A later scheduled tick cannot restore obsolete state.
* A connection or reconnect 1500 ms after a scheduled snapshot with SSE at 2000 ms and healthy fast native input receives fresh current state immediately, without a false stale indication or a subsequent older snapshot.
* Latest-state delivery remains shared across concurrent clients; one slow client cannot cause unbounded storage or additional native requests. Reconnect refreshes settings and state; duplicates and malformed metadata do not prolong freshness.
* Both source and browser deadlines equal 1.5 times the effective SSE period, with distinct receipt clocks. Test native gaps just below, at, and above that threshold, including a gap caused by a slow native setting. Repeated SSE snapshots of the cached sample must not postpone server expiry. A longer SSE period increases the source deadline but never changes its native receipt timestamp; IAS history retains its existing boundary.

Verify native cadence changes do not change this formula and cached SSE sends do not refresh native receipt time. Repeat terminal failure with native close held pending and confirm `disconnected` bypasses the ordinary SSE schedule before cleanup completes.
